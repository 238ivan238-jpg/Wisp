# Wisp development and delivery

The user installs Wisp on a Pixel 9 and expects future releases to appear inside the app.

User UI preferences: the input UI is only a movable floating microphone, without a keyboard panel, branding, language/mode chips, preview, ABC, undo, space/delete/Enter, or manual insert button. Tap starts/stops recording, hold opens settings, drag moves the icon. Insert processed text automatically into the current editor after recording stops; never send the message. Language/mode controls belong in settings. Use monochrome colors following the system light/dark theme. Reserve the system navigation area and keep touches outside the bubble available to the underlying app. Do not restore removed controls without the user's request.

The user now explicitly requested a small attached EN action below the microphone (since 1.0.10). Keep the movable VoiceControls compact (64 x 112 dp), with a 64 dp main microphone and 48 dp lower English action. Do not add a separate gear or other controls. Hold either action for settings and drag either to move both. Reserve navigation/cutouts for the whole pair; both actions must be in the legacy IME touch region. The requested recording limit is five minutes (since 1.0.8) in both services; use RecordingLimits for the recorder, timer/progress and statistics cap. Since 1.0.14, only active audio counts: the lower EN action becomes pause while recording and resume while paused; the upper action finishes. Do not change the selected mode on pause/resume. Processing runs after stop, without automatic chunking.

Dictation should produce edited written text, including grammar/explicit self-corrections and automatic lists, while preserving facts, negation and Russian/English technical terms. The single editor is called «Чистый текст», enabled by default, with automatic punctuation/paragraphs/lists and filler removal. Do not reintroduce separate message/notes modes: legacy choices map to this editor. Keep raw transcription available by turning the editor off and preserve an explicitly disabled editor on upgrade. Do not seed Whisper with generic language-description prose: it was echoed into a user's transcription. Without a user dictionary, omit its prompt field. Do not blacklist legitimate spoken English. Pass the dictionary as data to cleanup, never as system instructions. Mock transport tests check the data path; do not describe them as validation of live model language quality.

English translation is chosen per recording by the lower EN action. The upper microphone ALWAYS records without translation (clean or raw according to settings). EN selects translate for one session, including when normal processing is off, without changing preferences. Freeze the selected mode at start and use it through stop/processing/logs/statistics. Show EN on the recording/processing icon and timer; the upper action stops, while the lower pauses/resumes without switching mode. Disable both during processing. The former global translation switch is replaced by instructions; migrate stored translate mode to normal clean processing so the upper microphone cannot unexpectedly translate. Preserve facts/negation/names/technical terms; do not answer dictated requests.

Optional «Добавлять эмодзи» (since 1.0.9) defaults off and enables processing when selected. It adds a trusted style instruction to the existing clean/translation request, including model fallback; no extra request or transcription prompt. Since 1.0.12 the user requested MORE frequent emoji styling: ordinary suitable conversational messages should include an emoji, usually 1–3 in short text, up to 4–6 in longer text or alongside actual list items. Retain restraint for illness/grief/danger/conflict/formal/code-only topics, preserve meaning and words/list markers, and count existing emojis without duplicating them. Disabling normal processing turns emoji styling off; EN can still explicitly translate a single recording. Keep raw/failure output intact. Mock tests verify requests and Unicode handling, not real model styling quality.

Application UI since 1.0.12: fixed five-tab bottom navigation (Voice, Recordings/Recovery, Statistics, Diagnostics, Settings). Dictionary is now a settings detail page. No giant all-in-one setup feed, promotional headers, sandbox input or footer recommendations. Voice shows daily controls only; dictionary has its own saved editor under Settings; stats and diagnostics open their data directly. Settings is a compact row menu for Connection, Groq key, Updates and legacy keyboard, with details only after a tap. Keep system monochrome, short copy, readable labels/icons and 48 dp minimum targets; bottom navigation stays outside scrolling content and clear of system bars/cutouts. Preserve update checks and pending installation across tab changes/recreation; keep unsaved dictionary drafts, never save typed API keys in UI instance state. Do not remove logging, statistics or secure update validation while simplifying screens. Pixel settings are a visual reference, not a claim of reproducing a specific current external design.

Since 1.0.13 the user explicitly requires contextually INTEGRATED emojis: attach each to its relevant clause/sentence/list item, including natural prefix or mid-sentence positions; do not collect a decorative footer/emoji-only final paragraph. A naturally relevant sentence-final emoji remains allowed. Existing emojis and code/URLs/words must remain intact. Keep this instruction and examples in the existing processing request, not an output-moving regex or an extra model call. See docs/IDEAS.md for proposals; they are not implemented or authorized as a blanket roadmap. VPN involvement in the reported 403 remains unconfirmed; never silently bypass the user's VPN or automatically retry access denials as a supposed fix.

The user explicitly chose automatic insertion via accessibility to keep Gboard as the main keyboard. On Android 13+ use GboardCompanionService with FLAG_INPUT_METHOD_EDITOR and the public accessibility InputMethod API; the service must not retrieve the screen tree (canRetrieveWindowContent=false), replace the whole field, use the clipboard or send messages. Keep the overlay small and non-focusable; microphone recording runs as a bound microphone foreground service. A new/restarted input connection, password field or screen lock must cancel pending recording/insertion. The user enables the accessibility service and chooses Gboard in Android; do not programmatically bypass those controls. The former Wisp IME remains a fallback, especially on Android 9–12. Do not show two microphones when the Wisp IME is selected. No physical Pixel test has been performed in the cloud.

Do not require getSurroundingText to start recording or to allow a commit on an existing live connection (Messenger compatibility, since 1.0.11). Some editors support commitText but not context reads. A null/unsupported read permits one cursor/selection commit without guessed spaces; return SENT_WITHOUT_CONTEXT and log CONTEXT_UNAVAILABLE/UNCONFIRMED. Never retry it, claim confirmed insertion/word counts, or overwrite the whole field. Keep processing warnings visible even when read-back is unavailable. Malformed non-null context, missing connections, changed/closed editors and sensitive fields retain their guards.

Usage statistics are local aggregates only: sessions after valid recording stops, recording duration, words successfully committed/confirmed, up to 365 daily buckets (7/30-day charts and a rolling 365-day chart grouped by month), known filler phrases actually removed in successful normal cleanup, and bounded technical error categories. Never store transcript text, audio, arbitrary provider errors or credentials in statistics. Do not count translation differences as removed fillers. Preserve aggregate counters across updates; clearing needs an explicit action in the statistics screen. No historical data can be reconstructed for releases before 1.0.6 or for previously discarded daily buckets. Show totals/chart immediately in the Statistics tab, with ranked details collapsed; use the shared bottom navigation instead of the former stats back button.

Diagnostics: collect only bounded structured events (last 200), session ids, stages, model, mode, timings, HTTP codes, word counts, exception classes and app source frames. Never persist text, audio, keys, headers, URLs, request/response bodies, arbitrary exception messages or full device identifiers. Record unchanged model output explicitly. Export read-only JSON through the dedicated diagnostics FileProvider or Android document picker. There is no configured automatic upload endpoint or direct connection to this chat: the user shares/attaches the file. Never upload diagnostics to the public repository. Crash logging must persist before delegating to the existing uncaught-exception handler. Diagnostic collection begins with 1.0.7.

- Use the existing checkout. Do not create a worktree unless the user explicitly asks.
- Keep the update feed URL stable: branch `codex/wisp-android-v1`, file `downloads/latest.json`. Do not delete or repurpose this branch; installed apps depend on it.
- For Android behavior changes, increment `versionCode` and `versionName` in `app/build.gradle`. Never replace a published versioned APK with different bytes.
- Activate `source scripts/cloud-env.sh`; run `bash scripts/setup-cloud.sh`. Complete the relevant tests and lint before publishing. Preserve TLS, checksum and signing verification.
- Run `python3 scripts/prepare-release.py --notes '<brief user-facing changes>'` after a successful build. It checks the existing signing certificate, generates the versioned APK and updates the feed with its SHA-256/size/version. Run it again to check repeatability if the publisher changes.
- Deliver the new APK and `downloads/latest.json` in the same commit. When the user's task authorizes delivery, push the commit to `codex/wisp-android-v1` without force. Verify the public feed/download and actual client download checksum before reporting success. Preserve remote changes and stop to resolve divergence rather than force-pushing.
- After publishing, run `python3 scripts/verify-update-channel.py`. It exercises the actual Java update client against GitHub for both an older installed version and an already-current version, and compares the download to the local release APK. A completed Android install still needs a phone.
- Retain the private `.local/debug.keystore` for compatible updates. Never publish it, passwords, Groq keys, caches or `.local` contents. `downloads/Wisp-source.zip`, when refreshed, must exclude `downloads/`, build outputs and private files.
- Updater code must verify file size, SHA-256, package/version and the installed application's signing certificate before handing the APK to Android. It may not bypass the OS installation approval or attach Groq credentials to GitHub requests.
- Distinguish JVM/network checks from a completed installation on the physical phone. Do not claim a real Groq call or device installation passed unless observed.

Since 1.0.14, the user explicitly authorized recovery storage: up to 10 encrypted drafts in noBackupFilesDir for 7 days since their last checkpoint, pruned on next app/service use. Save finalized audio before any upload, the original text before cleanup, and finished text before insertion. AES-GCM uses a dedicated Android Keystore key. This recovery data is separate from diagnostics/statistics and must never be exported in their reports or uploaded to the repository. Recovery provides manual retry, explicit copy/text/audio export and delete. Confirmed clean insertions remove the draft; failures, cleanup fallbacks and unconfirmed handoffs retain it. Mark handoffs durably before commit; never automatically reinsert an unconfirmed/possibly accepted result. The small lower action temporarily becomes ↻ for retry in the same live editor. Once its input connection restarts, ↻ opens recovery instead of inserting into a different field. Never change Gboard, use automatic clipboard insertion or send messages. After a finalized recording/normal lifecycle cancellation, drafts survive processing cancellation and app restart; abrupt process death during an unfinished MP4 recording is not guaranteed recoverable.

Before each new recording, run a bounded asynchronous connectivity/key/model-list check; show only a short checking state and a concise error on failure. Successful /models access proves neither future /audio upload nor text generation acceptance: network/VPN/server state can change. Observe active VPN transport in connection settings/typed diagnostics without addresses, keys or hidden VPN bypass. Automatic network retries (proposal 4), per-app position (7), exact substitutions (14) remain discussion only; edge snapping/transparency/haptics and dictionary redesign were declined/deferred. Remove start vibration. The user will continue roadmap discussion after item 14.
